# Бэкенд проекта «Теплощит»

В этом репозитории сохранены серверные лабораторные работы №1–4; изменения для React-приложения ЛР6 находятся в ветке `lab6`. Сам React-фронтенд размещён отдельно: [Teploizolyatsiya-frontend](https://github.com/Rayana06/Teploizolyatsiya-frontend), ветка `lab6`. Серверные Handlebars-шаблоны оставлены для воспроизведения ранних лабораторных работ.

**Задание:** Создание базы данных `PostgreSQL` по теме работы, подключение БД к созданным трём шаблонам.

## PostgreSQL и TypeORM

**Тема:** оценка эффективности теплоизоляции здания. Услуга — карточка изоляционного материала.

Приложение использует NestJS, серверные Handlebars-шаблоны, PostgreSQL 17 и TypeORM. Реализованы ровно шесть HTTP-обработчиков: три GET; POST создания и POST публикации через ORM; POST логического удаления сырой SQL-командой `UPDATE WHERE CURRENT OF` через PostgreSQL-курсор `DECLARE/FETCH/CLOSE`.

## Первый запуск

1. Создайте `.env` по образцу `.env.example`. Если `.env` остался от лабораторной №1, значения PostgreSQL можно не добавлять — используются локальные значения по умолчанию.
2. Запустите `docker compose up -d`.
3. Выполните `npm install`, затем `npm run build` и `npm start`.
4. При первом старте TypeORM автоматически применит миграцию структуры.
5. Откройте Adminer: `http://localhost:8080`. Система — PostgreSQL; сервер — `insulation-postgres`; пользователь — `teploshchit`; пароль — `teploshchit`; база — `teploshchit` (либо значения из `.env`).
6. В Adminer откройте «SQL-команда» и выполните файл `database/adminer-seed.sql`. Так данные будут внесены именно через Adminer, как требует задание.
7. Откройте приложение: `http://localhost:3000/insulation-materials/catalog`.

MinIO лабораторной №1 остаётся источником медиа существующих карточек. Если URL пуст или изображение не загрузилось, чистая HTML-конструкция `<object><img></object>` показывает локальный файл SSR-сервера; для видео в разметке указан второй `<source>`. Оба файла лежат в `public/default-media`. Выбранные в форме новые файлы не имеют атрибута `name`, поэтому браузер не включает их в запрос. Все файлы, классы представлений, CSS-префиксы и URL используют единое предметное имя `insulation-materials`.

Итоговая предметная схема содержит четыре столбца в `users`, одиннадцать в `insulation_materials` и три в `insulation_material_likes`. Два поля по теме — `insulation_type` и `thickness_mm`. Количество лайков вычисляется из строк таблицы связей методом `loadRelationCountAndMap`, массив лайков в шаблоны не передаётся.

## Структура материалов для защиты

- `database/adminer-seed.sql` — первоначальное заполнение через Adminer.
- `database/defense-queries.sql` — готовые UPDATE/SELECT для требуемых скриншотов.
- `docs/lab2/ER-DIAGRAM.md` — итоговые таблицы, типы, длины, PK/FK и обязательность полей для Draw.io.
- `docs/lab2/DEFENSE.md` — порядок 22 скриншотов.
- `docs/lab2/CONTROL-QUESTIONS.md` — краткие ответы на контрольные вопросы.

## Проверка

При работающем PostgreSQL выполните `npm test`. Тесты проверяют схему, запрет каскадного удаления, единственность черновика, три страницы, медиа по умолчанию и полный цикл ORM/SQL.

Старые методы и состав ответов ЛР3 сохранены. Добавление повторяет два состояния страницы ЛР2: `POST /api/insulation-materials/draft/start` принимает название и необязательные фото/видео по кнопке «Далее»; `GET /api/insulation-materials/draft` возвращает черновик; `PATCH /api/insulation-materials/draft/:id` заполняет вторую группу полей; `PUT /api/insulation-materials/:id/publish` публикует его. Для каждого изменения проверяется сессия и владелец.
